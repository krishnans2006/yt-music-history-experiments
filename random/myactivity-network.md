# Direct-response benchmark and API capture

The [network tool](myactivity-network.js) tests faster transports before building a full-range replacement for the page-rendering extractor. It fetches raw responses without navigating, rendering Google UI, or waiting for the DOM to settle. It also observes the current history read RPC and can replay one captured request from the same browser session. It is a bounded protocol/latency experiment, not yet a complete listen-history exporter.

1. Pause the old extractor. Open your logged-in [My Activity YouTube History](https://myactivity.google.com/product/youtube) page with the intended account and filters.
2. Paste `random/myactivity-network.js` into DevTools → Console.
3. Select the completed 40-minute Radioactive extractor export in the file input, then click **Recover reference interval (fast)**. It first checks a known empty interval from that export, then walks backward using native timestamps and validates every result against the reference. It downloads **`myactivity-network-report.json`** automatically. Save it under `media/` for analysis. The optional **Probe current route (3 reads)** and older nine-read transport comparison remain available, but both discovery runs have already confirmed the current route.
4. To capture the live RPC, scroll a history view with more results or apply a date filter after installing the tool. Once **Replay captured history read** becomes enabled, click it, then download the updated JSON. A full page reload removes the recorder; paste it again if needed. **Stop** aborts the benchmark and restores the original fetch/XHR functions.

The RPC lead, `y3VFHd` at `/_/FootprintsMyactivityUi/data/batchexecute`, is documented for watch/search history in the [2026 conference proceedings, pp. 134–135](https://fliphtml5.com/ypgup/2026CSHONAM/). The older `/item?...&jspb=1` route appears in [2019 forensic research on My Activity](https://lifs.hallym.ac.kr/pubs/brhan_apibasedcloud_2019.pdf), for Assistant data. Its continued availability and usefulness for Music are unverified; a failed legacy probe does not invalidate the current-route results. Neither lead supplies a verified current Music request schema, so the tool preserves actual responses instead of inventing field positions.

**What the report contains.** Response sizes and measured network/body-read times; safely decoded JSON, batch payloads and activity-bearing bootstrap data; an inventory and timestamp/watch-URL candidates from every decoded bootstrap block; static watch links and nearby text extracted from server HTML without rendering; captured history arguments; and per-probe failures. Both scalar epochs and `[seconds, nanoseconds]` timestamp candidates are supported. Numeric candidates can also be query bounds or other metadata. They are not labelled as exact listen events. Continuations and record semantics still need to be identified from the live data. Raw HTML, cookies, authorization headers and the form's `at` token are not exported. The replayable Request and session fields remain in memory; known `at` values are redacted if they recur inside exported data. The report still contains private activity data.

**First live network report verified.** The supplied `media/myactivity-network-report.json` contains six HTTP-200 GET responses, three failed legacy fetches, and zero RPC captures/replays. Successful requests took 391–696 ms (median 417 ms) and returned about 1.33 MB of decoded HTML each. Adding `jspb=1` did not yield JSON or change the preserved summary data. The legacy failures have no HTTP status; because the requests reject redirects, their exact cause is unproven.

The preserved `ds:5` data has product ID 26 / label YouTube and a two-number timestamp. Interpreting the numbers as epoch seconds plus nanoseconds yields:

| Window | Product-summary timestamp, UTC | Corrected reference match |
|---|---|---|
| Broad | 2024-12-07 04:36:40.589956 | 1 of 12 intervals |
| Early | 2024-12-07 04:08:22.120717 | 1 of 3 intervals |
| Middle | 2024-12-07 04:17:48.156926 | 1 of 3 intervals |

This interpretation is consistent with [protobuf's seconds/nanoseconds timestamp fields](https://protobuf.dev/reference/protobuf/google.protobuf/#timestamp) and all three known reference brackets. The prior report's broad 0-of-12 comparison was a decoder false negative: treating the timestamp as `04:36:40.000` discarded the fractional component and moved it outside the narrow bracket. The decoder and regression tests now preserve nanoseconds exactly.

These are product-summary timestamp candidates, not yet identified Music records: no video URL was preserved. The first tool version retained only 3 of 9 bootstrap blocks and did not capture the server-rendered watch links. Consequently this report cannot establish whether the complete HTML contains more event data, or whether all repeat consolidation happens server-side. The updated tool examines candidate fields in every block and captures static watch-link context without exporting raw HTML. Derived verification is in `media/myactivity-network-analysis.json`; the original report is unchanged.

**Proposed next experiment.** Use the working current-route response and native timestamp for a small backward-cursor prototype over the known 40-minute interval: keep the lower bound fixed, put the next maximum one microsecond before the returned time, and verify that all 12 reference brackets appear before a recognizable empty result. If that semantics holds, this is approximately 12 positive reads plus a final empty read instead of 193 bisection queries. Record/video/app association and empty-result behavior still need validation. Inspect the static HTML watch links and, separately, capture one genuine UI history RPC by scrolling a longer history view after installing the recorder. The probe requests deliberately use the original fetch function and do not themselves create RPC captures. Prefer a smaller paginated RPC transport once its schema is observed; scale independent historical windows with measured concurrency after the 12-event test passes. The first nine requests do not establish a sustained account rate limit or a full-export completion time.

**Second report and implemented cursor pilot.** `media/myactivity-network-report(1).json` confirms three successful GETs at 372–409 ms (median 383 ms), each with all nine bootstrap blocks inventoried. The scanner finds no watch URLs in the blocks or static HTML, and there are still no captured/replayed RPCs. The same precise product-summary timestamps match one reference bracket per window. This validates the GET/timestamp route, but does not supply Music/video identity. Derived verification is in `media/myactivity-network-second-analysis.json`.

The **Recover reference interval (fast)** button now implements the bounded experiment. It requires the completed Radioactive reference export, including its saved empty-query evidence. It makes one empty-control read followed by dependent native-timestamp reads, retaining the normal access checks, pacing and error stops. It accepts an empty summary or a summary strictly before the lower bound as an empty-control result; it stops on an in-range/non-progressing result, unknown data structure, out-of-bounds time, an unexpected/duplicate reference interval, or premature termination. The next `max` is the largest integer microsecond strictly before the returned nanosecond timestamp. No second-level bisection or Google UI rendering is used.

Success requires every loaded reference interval to match exactly once and a verified end condition. For the supplied 12-event reference, that normally means **14 reads**: one control, twelve observations, and one final empty/before-range result (plus the robots check). The dependent cursor uses one worker; later independent windows can use the pool. Results are saved under `cursor` with exact timestamp values, matched reference indices and all query evidence. Recording identity is labelled as reference-supplied, not independently verified from the product summary. This pilot is not a full-history Music exporter and has not yet been run against the user's live account. Offline simulations verify success, lower-bound summary behavior, non-progress stops and premature-empty stops.

**Validated reference interval.** The user's completed Radioactive export contains **12** separate observations, approximately 3:09 apart, bracketed to 937–938 ms; both precise timestamps from MyActivity JSON fall in the corresponding brackets. It took 196 queries and 32:50 wall time. See [the findings](myactivity-website-findings.md). Loading that export lets each probe report how many of those known intervals contain a timestamp candidate in the raw response. The broad window has 12 expected intervals; the early and middle windows each have 3. This distinguishes a possible bulk response from a response exposing only the latest occurrence. A numerical match alone still does not establish that a field is the recording's event timestamp: verify the association in the response structure. The reference check adds no network requests.

**Concurrency and access.** The default is at most two active reads, with a 500 ms gap between starts, for this nine-request experiment. `OPTIONS.concurrency` and `OPTIONS.startGapMs` control these values. Longer applicable robots crawl delays take precedence. The tool uses the same cross-tab lock as the old extractor, checks the existing throttle cooldown, respects disallowed paths, and stops/cancels the batch on access errors, HTTP 429 or server errors. HTTP 429/503 creates a cooldown of at least 24 hours and honors a longer available `Retry-After`. There are no automatic retries, proxies, alternate accounts or CAPTCHA bypasses. These defaults are not a published Google quota or a guarantee against account flags. A larger worker count should be evaluated from measured latency and server responses, not assumed to yield linear speedup against one account/backend.

Passive capture never generates requests. Only POST batches consisting entirely of the observed history-read RPC are eligible for replay. Other RPCs are metadata-only; deletion and mixed batches cannot become replay templates. The tool reads the existing session and does not modify listening history.

**Next implementation gate.** Use the report to select a working direct transport, identify exact timestamps and continuation fields, and compare broad versus narrow results for repeat preservation. A complete replacement can then fetch pages directly and move bounds using returned timestamps, with a measured worker pool for independent intervals. Exact timestamps can remove the many bisection requests per event as well as the rendering wait. Until the live response shape is inspected, there is no justified full-range speed or completeness claim.

Tests cover the JSON/batch/bootstrap decoders, timestamp candidates, read-only replay eligibility, bounded concurrency/cancellation, credential redaction, fetch/XHR capture and replay, access rules, and throttle stops.
