# Direct-response benchmark and API capture

The [network tool](myactivity-network.js) tests faster transports before building a full-range replacement for the page-rendering extractor. It fetches raw responses without navigating, rendering Google UI, or waiting for the DOM to settle. It also observes the current history read RPC and can replay one captured request from the same browser session. It is a bounded protocol/latency experiment, not yet a complete listen-history exporter.

1. Pause the old extractor. Open your logged-in [My Activity YouTube History](https://myactivity.google.com/product/youtube) page with the intended account and filters.
2. Paste `random/myactivity-network.js` into DevTools → Console.
3. Optionally select the completed 40-minute extractor export in the file input as a reference, then click **Probe APIs (9 reads)**. The tool tests the broad, early and middle Radioactive windows using the current page route, that route with `jspb=1`, and the historical `/item?jspb=1` route. It downloads **`myactivity-network-report.json`** automatically. Save it under `media/` for analysis.
4. To capture the live RPC, scroll a history view with more results or apply a date filter after installing the tool. Once **Replay captured history read** becomes enabled, click it, then download the updated JSON. A full page reload removes the recorder; paste it again if needed. **Stop** aborts the benchmark and restores the original fetch/XHR functions.

The RPC lead, `y3VFHd` at `/_/FootprintsMyactivityUi/data/batchexecute`, is documented for watch/search history in the [2026 conference proceedings, pp. 134–135](https://fliphtml5.com/ypgup/2026CSHONAM/). The older `/item?...&jspb=1` route appears in [2019 forensic research on My Activity](https://lifs.hallym.ac.kr/pubs/brhan_apibasedcloud_2019.pdf), for Assistant data. Its continued availability and usefulness for Music are unverified; a failed legacy probe does not invalidate the current-route results. Neither lead supplies a verified current Music request schema, so the tool preserves actual responses instead of inventing field positions.

**What the report contains.** Response sizes and measured network/body-read times; safely decoded JSON, batch payloads and activity-bearing bootstrap data; candidate timestamp values with their array paths; captured history arguments; and per-probe failures. Numeric candidates can also be query bounds or other metadata. They are not labelled as exact listen events. Continuations and record semantics still need to be identified from the live data. Raw HTML, cookies, authorization headers and the form's `at` token are not exported. The replayable Request and session fields remain in memory; known `at` values are redacted if they recur inside exported data. The report still contains private activity data.

**Validated reference interval.** The user's completed Radioactive export contains **12** separate observations, approximately 3:09 apart, bracketed to 937–938 ms; both precise timestamps from MyActivity JSON fall in the corresponding brackets. It took 196 queries and 32:50 wall time. See [the findings](myactivity-website-findings.md). Loading that export lets each probe report how many of those known intervals contain a timestamp candidate in the raw response. The broad window has 12 expected intervals; the early and middle windows each have 3. This distinguishes a possible bulk response from a response exposing only the latest occurrence. A numerical match alone still does not establish that a field is the recording's event timestamp: verify the association in the response structure. The reference check adds no network requests.

**Concurrency and access.** The default is at most two active reads, with a 500 ms gap between starts, for this nine-request experiment. `OPTIONS.concurrency` and `OPTIONS.startGapMs` control these values. Longer applicable robots crawl delays take precedence. The tool uses the same cross-tab lock as the old extractor, checks the existing throttle cooldown, respects disallowed paths, and stops/cancels the batch on access errors, HTTP 429 or server errors. HTTP 429/503 creates a cooldown of at least 24 hours and honors a longer available `Retry-After`. There are no automatic retries, proxies, alternate accounts or CAPTCHA bypasses. These defaults are not a published Google quota or a guarantee against account flags. A larger worker count should be evaluated from measured latency and server responses, not assumed to yield linear speedup against one account/backend.

Passive capture never generates requests. Only POST batches consisting entirely of the observed history-read RPC are eligible for replay. Other RPCs are metadata-only; deletion and mixed batches cannot become replay templates. The tool reads the existing session and does not modify listening history.

**Next implementation gate.** Use the report to select a working direct transport, identify exact timestamps and continuation fields, and compare broad versus narrow results for repeat preservation. A complete replacement can then fetch pages directly and move bounds using returned timestamps, with a measured worker pool for independent intervals. Exact timestamps can remove the many bisection requests per event as well as the rendering wait. Until the live response shape is inspected, there is no justified full-range speed or completeness claim.

Offline checks: `node random/myactivity-network.test.cjs` and `node random/myactivity-network.simulation.test.cjs`. Tests cover the JSON/batch/bootstrap decoders, timestamp candidates, read-only replay eligibility, bounded concurrency/cancellation, credential redaction, fetch/XHR capture and replay, access rules, and throttle stops. No authenticated Google benchmark was run in the coding environment.
