# Full past Music export

Use [myactivity-fast.js](myactivity-fast.js), the complete standalone browser script. Refresh your logged-in [My Activity YouTube History page](https://myactivity.google.com/product/youtube) to remove the old tools, select the intended account, and use the English interface. Paste the entire file into DevTools → Console. No installation, copied headers, or captured API request is needed.

Click **Validate & export / Resume**. The default range is January 1, 1970 through the instant the script was installed. That includes history older than the first Takeout observation; empty old years cost one history read each, plus a native-summary check if an empty reply carries an ambiguous continuation. The cutoff stays fixed on resume. With the current page's session metadata available, the script uses bounded `y3VFHd` reads directly. It independently checks all 12 known Radioactive video/timestamp observations against native GET summaries, determines endpoint inclusivity using positive boundary controls, and verifies two adjacent empty microsecond intervals. It then automatically exports the full selected range through the bounded API. There is no separate benchmark or confirmation step.

Keep the main tab open. The API path opens no popup. If page session metadata is unavailable, the older native/HTML/popup transport remains a fallback and requires its window to remain open. **Pause** stops collection and downloads JSON. **Download JSON** also saves committed progress while collection is running. Completion and errors trigger a download too: `myactivity-fast-<run-id>.json`. Save it under `media/`. Its `events` list contains only YouTube Music `Watched` observations, ordered by exact UTC timestamp; separate repeats remain separate events. `coverage.complete` becomes true only after the reference check and every requested range finish.

The live range table shows each year range's current phase, cursor/activity date in UTC, saved Music count and calendar coverage bar. Active rows are highlighted; queued, completed and resumable ranges remain visible in the scrollable table. Hover over a range or coverage bar for its exact date bounds and scanned/remaining intervals. Bars reflect committed cursor progress through calendar time, not an estimated percentage of listens. Reference validation has its own live status. Restoring an older checkpoint reconstructs per-range counts from saved events locally, without requests to Google. To upgrade a running script, click **Pause**, refresh, paste the updated standalone file and resume.

Reloading and pasting the script again restores the latest run in the same browser profile/account. Click **Validate & export / Resume** to continue from its committed cursors. Do not clear the site's IndexedDB during collection. JSON downloads are readable backups and contain progress metadata; file import into this new exporter is not implemented. Older popup-extractor checkpoints use a different database and are left intact.

**How this preserves repeats.** For each independent year range, the bounded API returns history records. The exporter saves Music watches in the newest timestamp group and moves the logical inclusive maximum back one microsecond. The lower bound remains fixed. Earlier repeats then become the newest listen of that recording inside the shrinking range. It examines ordinary YouTube observations too: a later YouTube watch of the same recording could otherwise hide an earlier Music listen. It never jumps past the oldest row of a consolidated page or deduplicates by video/day. Continuations are followed only when an entire full page shares the newest timestamp and more simultaneous records could remain. Boundary controls use one page only. Empty replies with continuation tokens require an independently empty native summary before completing a history range; inconsistent results and non-progressing pages stop collection.

**Bounded API schema.** The public frontend bundle identified in the failed popup export provided the missing schema. Its `bD` helper maps the URL's microsecond bounds through `$C` into seconds/nanoseconds pairs; `aD` stores that interval in filter (`az`) field 4. The `ez` request carries that filter at field 1, continuation at 2 and page size at 3. The resulting arguments are `[[null,["youtube"],null,[[minSeconds,minNanos],[maxSeconds,maxNanos]]],continuation,100]`. The script reads `SNlM0e`, `FdrFJe` and the build identifier from the already loaded page's `WIZ_global_data`, keeps them in memory, and posts only the observed history-read RPC. No session fields are copied into downloads. Endpoint inclusivity is measured and normalized; every returned timestamp is still audited against the logical requested bounds. See [the schema provenance](myactivity-rpc-schema.md).

The earlier 12-event native timestamp cursor was validated live in 7.671 seconds. When session metadata is unavailable, the legacy identity fallback uses these transports:

1. Decode matching history records from the GET's bootstrap arrays or Wiz `data-p`/`data-proto` attributes, without evaluating JavaScript.
2. If history cards are present as HTML, read the exact point interval directly and parse their text/links, including Google redirect links.
3. Otherwise open that exact point interval in the reusable popup and read its completed cards. No second-level bisection or pagination scrolling is performed.

**Observed popup failure and current validation status.** The user-run fallback loaded the correct Radioactive card at `2024-12-07T04:36:40.589956Z`, but its footer read `Unable to load more. Retry`. No event or cursor step was committed. The updated fallback reports this as an incomplete-results error immediately; it never clicks Retry or treats that footer as the end. The bounded API path avoids that UI dependency. It has passed offline protocol and browser simulations but **has not yet passed the authenticated 12-observation check**; that check runs automatically before full export. The script stops and downloads evidence if bounds, identities or reference timestamps fail validation. Neither the prior timestamp-only speedup nor simulated API throughput is a measured full-export speedup.

The first API attempt stopped with `Unknown history RPC payload` before committing a validation step. Its checkpoint omitted the actual reply, so that file cannot establish whether the payload was null/a service error or carried extra protobuf fields. The decoder now accepts optional trailing fields while validating the known rows and continuation, distinguishes service errors from empty results, and saves redacted decoded failure evidence under `run.diagnostics.rpcFailure` plus the bounded arguments under `lastRPC`. A null result never counts as an empty history page. Resource-exhausted service errors stop the run and apply the throttle cooldown. Existing failed Network response bodies can be inspected without issuing another request.

The subsequently saved `myactivity-rpc-failure.txt` resolves the response question: it is a valid multi-frame batchexecute reply with a null `y3VFHd` result and service status 3 (`INVALID_ARGUMENT`, as defined in [Google's canonical codes](https://github.com/googleapis/googleapis/blob/master/google/rpc/code.proto)). A regression test decodes that exact file without a JSON framing error. This establishes a rejected request, not a history-schema change. The corresponding request arguments are still needed to tell whether the rejected call was the broad history read or a boundary control; no parameter correction is claimed from the response alone.

The matching saved request pinpoints the bug: it covers `1733546200589956` through `1733546200589957` microseconds and includes a nonempty continuation token. This is a follow-up page of the one-microsecond lower-bound control. The initial broad read had already passed its comparison with the native timestamp before this control ran. The fix stops controls after their first page and avoids chasing short-page continuations during latest-timestamp extraction. Regression simulations reproduce the same status-3 failure when such a continuation is followed, then verify that all repeats export without sending that request. The raw saved form also includes a session field; diagnostics and regression checks extract only `f.req`.

Two year ranges can fetch concurrently. All GETs, API reads and fallback popup navigations share a 500 ms minimum start gap; fallback popup identity checks use one window sequentially. There are no session/day action caps. Longer applicable robots delays take precedence. The script honors the shared cross-tab extractor lock, previous cooldowns, robots restrictions and HTTP/access/traffic errors. It performs no history mutations, playback, automatic retries, account switching, proxies or verification bypasses. HTTP 429/503 and explicit traffic warnings create a cooldown of at least 24 hours, extended for a longer Retry-After. These are pacing/error controls, not a published safe Google quota.

Events and the next cursor commit in one IndexedDB transaction. Commit operations are serialized across workers so one worker cannot persist another worker's uncommitted cursor after a failed write. Reference observations are stored separately from the full-range `events` list. Query receipts retain bounds and timestamps; failure diagnostics can include ordinary YouTube cards and public frontend script URLs. Cookies, session headers and form tokens are not exported. Enumerating retained Google activity is not proof that every physical playback was logged or completed. API records retain their available microsecond precision; the native GET decoder stops if it encounters finer precision it cannot safely isolate. A singleton inclusive API interval is widened only downward by one microsecond to avoid a zero-width request, then older overscan rows are excluded; adding older activity cannot hide the newer target listen.

**Why the earlier captured RPC was insufficient.** The supplied `myactivity-bounded-response.txt` is identical to the recent unfiltered response in report (3): all 100 rows are from October–November 2026, outside the requested December 2024 interval. That capture omitted filter field 4. The bounded request now uses the schema traced from Google's own public code; it does not reuse the unfiltered continuation as a starting cursor.
