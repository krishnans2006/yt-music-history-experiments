# Full past Music export

Use [myactivity-fast.js](myactivity-fast.js), the complete standalone browser script. Refresh your logged-in [My Activity YouTube History page](https://myactivity.google.com/product/youtube) to remove the old tools, select the intended account, and use the English interface. Paste the entire file into DevTools → Console. No installation, copied headers, or captured API request is needed.

Click **Validate & export / Resume**. The default range is January 1, 1970 through the instant the script was installed. That includes history older than the first Takeout observation; empty old years cost one GET each. The cutoff stays fixed on resume. The button first recovers and checks the exact video ID and timestamp of all 12 known Radioactive observations, then verifies that the adjacent microseconds around the last observation return empty using the identity transport in use. Those empty controls detect point filtering rounded to whole seconds even if the 12 positive queries appear correct. After that succeeds, it starts the full selected range automatically. There is no separate benchmark or confirmation step.

Keep the main tab and the one fallback popup open. **Pause** stops collection and downloads JSON. **Download JSON** also saves committed progress while collection is running. Completion and errors trigger a download too: `myactivity-fast-<run-id>.json`. Save it under `media/`. Its `events` list contains only YouTube Music `Watched` observations, ordered by exact UTC timestamp; separate repeats remain separate events. `coverage.complete` becomes true only after the reference check and every requested range finish.

Reloading and pasting the script again restores the latest run in the same browser profile/account. Click **Validate & export / Resume** to continue from its committed cursors. Do not clear the site's IndexedDB during collection. JSON downloads are readable backups and contain progress metadata; file import into this new exporter is not implemented. Older popup-extractor checkpoints use a different database and are left intact.

**How this preserves repeats.** For each independent year range, a bounded GET supplies the newest YouTube product timestamp. The exporter identifies activity at that exact timestamp, saves Music watches, and moves the inclusive maximum back one microsecond. The lower bound remains fixed. Earlier repeats then become the newest listen of that recording inside the shrinking range. It examines ordinary YouTube observations too: a later YouTube watch of the same recording could otherwise hide an earlier Music listen. It does not jump past the oldest row of a consolidated page or deduplicate by video/day.

The earlier 12-event native timestamp cursor was validated live in 7.671 seconds. Identity is added using these transports, in order:

1. Decode matching history records from the GET's bootstrap arrays or Wiz `data-p`/`data-proto` attributes, without evaluating JavaScript.
2. If history cards are present as HTML, read the exact point interval directly and parse their text/links, including Google redirect links.
3. Otherwise open that exact point interval in the reusable popup and read its completed cards. No second-level bisection or pagination scrolling is performed.

The new identity transports and their integrated reference check have **not yet been run against the authenticated account**. The script stops and downloads diagnostic evidence if timestamps, bounds or card identities cannot be validated; it does not advance the cursor past an unidentified observation. Some source formats may require further decoder work. If raw HTML lacks identity data, the popup fallback will still incur page-load time. The 257× timestamp-only pilot speedup must not be presented as the measured full-export speedup.

Two year ranges can fetch concurrently. All GETs and popup navigations share a 500 ms minimum start gap; popup identity checks use one window sequentially. There are no session/day action caps. Longer applicable robots delays take precedence. The script honors the shared cross-tab extractor lock, previous cooldowns, robots restrictions and HTTP/access/traffic errors. It performs no history mutations, playback, automatic retries, account switching, proxies or verification bypasses. HTTP 429/503 and explicit traffic warnings create a cooldown of at least 24 hours, extended for a longer Retry-After. These are pacing/error controls, not a published safe Google quota.

Events and the next cursor commit in one IndexedDB transaction. Commit operations are serialized across workers so one worker cannot persist another worker's uncommitted cursor after a failed write. Reference observations are stored separately from the full-range `events` list. Query receipts retain bounds and timestamps; failure diagnostics can include ordinary YouTube cards and public frontend script URLs. Cookies, session headers and form tokens are not exported. Enumerating retained Google activity is not proof that every physical playback was logged or completed. Sub-microsecond source timestamps stop the run rather than being rounded past.

**Why not the captured RPC?** The supplied `myactivity-bounded-response.txt` is identical to the recent unfiltered response in report (3): all 100 rows are from October–November 2026, outside the requested December 2024 interval. Its request URL has no time bounds, and its `f.req` is identical to the unfiltered continuation. It cannot serve as the repeat-preserving cursor. The direct bounded GET route remains independently validated.

They cover native precision/bounds, collapsed same-track activity, cross-app hiding of Music repeats, both server identity paths, popup identification, simultaneous timestamps, reference validation, year coverage, concurrent workers, pacing, atomic rollback, pause/resume, ignored bounds, access restrictions and throttling.
